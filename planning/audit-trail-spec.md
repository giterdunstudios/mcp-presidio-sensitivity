# Engineering Spec: Audit Trail

**Status:** `ready-for-implementation`
**Stream:** Phase 1 — Stream 2
**Depends on:** structured-logging-spec.md (JSON formatter and service fields must be in place)
**Feeds into:** otel-spec.md (audit records carry `trace_id` from OTel span once instrumented)
**Last updated:** 2026-03-24

---

## Purpose

Every completed scan — regardless of decision — must produce an immutable audit record that
answers the question: *who asked, when, and what was the outcome?*

The audit record is the authoritative non-repudiation trail for the sensitivity classification
service. It must:
- Be written for every scan that reaches the analysis stage (including `block` decisions)
- Be written when the worker returns an error (the caller attempted a scan; that matters)
- Never contain payload content, entity text, or any field that could reconstruct what was scanned
- Be distinguishable from application logs so it can be queried independently

Audit records are **not** the structured application logs described in
`structured-logging-spec.md`. They are a separate logical stream written to the same
stdout pipeline but identified by a dedicated logger name and `event_type` field.

---

## What Triggers an Audit Record

An audit record is written in the MCP server's `classify_payload_sensitivity` tool handler:

| Trigger | `decision` in record | `scan_id` source |
|---|---|---|
| Worker returns a successful scan result | Value from worker (`allow` / `block` / `flag`) | From `WorkerScanResponse.scan_id` |
| Worker raises `WorkerError` (any reason) | `"error"` | Generated by MCP server (`uuid.uuid4()`) |

Records are written **after** `call_worker()` returns or raises — never before (to avoid
recording scans that were never attempted due to auth failure or request rejection at the
MCP layer).

Auth denials (401/403) and request rejections (413/415/400) do **not** produce audit records.
Those events are covered by structured application logs at `WARNING` level.

## Audit Record Schema

### Mandatory fields (every record)

| Field | Type | Value |
|---|---|---|
| `timestamp` | string | ISO 8601 UTC — `datetime.now(tz=timezone.utc).isoformat()` |
| `event_type` | string | Always `"audit"` — makes the record filterable without logger-name parsing |
| `audit_event` | string | Always `"scan_completed"` — reserved for future event types |
| `scan_id` | string | UUID string — from worker response, or generated on error |
| `correlation_id` | string | UUID — from `_current_correlation_id` context var |
| `trace_id` | string | OTel trace ID if active span exists; falls back to `correlation_id` until OTel is instrumented |
| `caller_subject` | string | JWT `sub` claim — from `_current_caller_subject` context var (see implementation notes) |
| `decision` | string | `allow` / `block` / `flag` / `error` |
| `service_name` | string | `"mcp-presidio-sensitivity"` — injected by `_ServiceContextFilter` |
| `service_version` | string | From env var — injected by `_ServiceContextFilter` |
| `environment` | string | From env var — injected by `_ServiceContextFilter` |

### Conditional fields (present on successful scan; absent on error)

| Field | Type | Value |
|---|---|---|
| `sensitivity_detected` | bool | From `WorkerScanResponse.sensitivity_detected` |
| `max_severity_band` | string | From `WorkerScanResponse.max_severity_band` — `null` if no findings |
| `matched_categories` | list[str] | From `WorkerScanResponse.matched_categories` |
| `findings_count` | int | From `WorkerScanResponse.confidence_summary.findings_count` |
| `policy_profile` | string | From `WorkerScanResponse.policy_profile` |
| `detector_version` | string | From `WorkerScanResponse.detector_version` |

### Conditional fields (present on error only)

| Field | Type | Value |
|---|---|---|
| `error_code` | string | From `WorkerError.error_code` |

### Fields that must NEVER appear

Same prohibition as `structured-logging-spec.md`:
`content`, `text`, `payload`, `entity_text`, `entity_value`, `start`, `end`, `offset`,
any field derived from the payload being classified.

## Implementation Plan

### Context variable — `caller_subject`

The `classify_payload_sensitivity` tool handler has no access to `request.state` — it
receives only its declared parameters. `caller_subject` is currently only available on
`request.state.caller_subject`, set by `JWTAuthMiddleware`.

**Required change to `main.py`:** add a second context variable alongside
`_current_correlation_id`:

```python
_current_caller_subject: ContextVar[str] = ContextVar(
    "_current_caller_subject", default="unknown"
)
```

In `JWTAuthMiddleware.dispatch()`, set it alongside `_current_correlation_id`:
```python
caller_token = _current_caller_subject.set(caller_subject)
# ... (reset in finally / return paths the same way as correlation_id token)
```

The tool handler then reads both:
```python
correlation_id  = _current_correlation_id.get(str(uuid.uuid4()))
caller_subject  = _current_caller_subject.get("unknown")
```

---

### New module: `src/mcp_server/audit/`

**`src/mcp_server/audit/__init__.py`** — empty package marker.

**`src/mcp_server/audit/trail.py`** — audit record writer.

```python
"""
Audit trail writer for the MCP sensitivity server.

Writes one structured log record to the audit logger on every scan attempt
that reaches the worker — success or failure.  The audit logger uses the same
JsonFormatter as the application logger; records are identifiable by:
  - logger: "mcp-presidio-sensitivity.audit"
  - event_type: "audit"

No payload content, entity text, or offset data may appear in any audit record.
This function has no `content` parameter and must never be given one.
"""

import logging
import uuid
from typing import Optional

from backend.models import WorkerScanResponse
from backend.worker_client import WorkerError

_audit_logger = logging.getLogger("mcp-presidio-sensitivity.audit")


def write_audit_record(
    *,
    correlation_id: str,
    caller_subject: str,
    result: Optional[WorkerScanResponse] = None,
    error: Optional[WorkerError] = None,
) -> None:
    """
    Emit one audit record.  Exactly one of `result` or `error` must be provided.

    Args:
        correlation_id:  Request correlation UUID from context var.
        caller_subject:  JWT `sub` claim from context var.
        result:          Successful WorkerScanResponse — present on happy path.
        error:           WorkerError — present when worker call failed.

    Security:
        This function has no `content` parameter.  It must never receive payload data.
    """
```

The function body:
- Determines `decision`: `result.decision` if result, else `"error"`
- Determines `scan_id`: `str(result.scan_id)` if result, else `str(uuid.uuid4())`
- Builds `extra` dict with all mandatory fields
- Adds conditional fields from `result` if present
- Adds `error_code` from `error` if present
- Calls `_audit_logger.info(...)` on success, `_audit_logger.warning(...)` on error

---

### Context variable reset discipline

`_current_caller_subject` must be reset on **every exit path** from `JWTAuthMiddleware.dispatch()`,
identical to the existing `_current_correlation_id` pattern. There are four exit paths:

1. Exempt path early return (before auth check)
2. `TokenMissingError` early return (401)
3. `TokenInvalidError` early return (401)
4. Scope denial early return (403)
5. Normal completion after `call_next(request)`

Each path that resets `correlation_token` must also reset `caller_subject_token`. Missing
a reset causes the previous request's `caller_subject` to bleed into the next request on
that coroutine, which would corrupt audit records in high-concurrency scenarios.

Pattern:
```python
caller_subject_token = _current_caller_subject.set(caller_subject)
# ... on every return path:
_current_caller_subject.reset(caller_subject_token)
```

### Call site: `classify_payload_sensitivity` in `main.py`

Replace the current try/except block:

```python
# current:
try:
    result = await call_worker(...)
    return result.model_dump(mode="json")
except WorkerError as exc:
    raise RuntimeError(f"{exc.error_code}: {exc.message}") from exc

# updated:
correlation_id = _current_correlation_id.get(str(uuid.uuid4()))
caller_subject = _current_caller_subject.get("unknown")

try:
    result = await call_worker(...)
    write_audit_record(
        correlation_id=correlation_id,
        caller_subject=caller_subject,
        result=result,
    )
    return result.model_dump(mode="json")
except WorkerError as exc:
    write_audit_record(
        correlation_id=correlation_id,
        caller_subject=caller_subject,
        error=exc,
    )
    raise RuntimeError(f"{exc.error_code}: {exc.message}") from exc
```

### `trace_id` resolution in `write_audit_record`

Until OTel is instrumented (Stream 4), `trace_id` falls back to `correlation_id`.

The import is attempted **once at module load time** via a module-level flag — not on every
call. A per-call try/except would silently degrade on import errors and obscure the
dependency boundary:

```python
# At module level in audit/trail.py:
try:
    import opentelemetry.trace as _otel_trace
    _OTEL_AVAILABLE = True
except ImportError:
    _otel_trace = None  # type: ignore
    _OTEL_AVAILABLE = False


def _resolve_trace_id(fallback: str) -> str:
    if _OTEL_AVAILABLE:
        span = _otel_trace.get_current_span()
        ctx = span.get_span_context()
        if ctx.is_valid:
            return format(ctx.trace_id, "032x")
    return fallback
```

`write_audit_record` calls `_resolve_trace_id(correlation_id)` to populate the `trace_id`
field. Once OTel is instrumented and `opentelemetry` is installed, `_OTEL_AVAILABLE` is
`True` and the real trace ID is used automatically.

## Acceptance Criteria

1. Every call to `classify_payload_sensitivity` that reaches `call_worker()` produces
   exactly one audit record in pod stdout.
2. Audit records are identifiable by `logger == "mcp-presidio-sensitivity.audit"` and
   `event_type == "audit"`.
3. Records for `block` decisions are present (not suppressed).
4. Records for worker errors have `decision == "error"` and include `error_code`.
5. `caller_subject` in the audit record matches the `sub` claim in the token used for
   the request.
6. `scan_id` in the audit record matches the `scan_id` in the tool response (success path).
7. No audit record contains `content`, `text`, `entity_text`, `start`, `end`, or `offset`
   as a field key.
8. `trace_id` is present in every record; before OTel is active, it equals `correlation_id`.
9. Auth denials and request rejections (401/403/413/415/400) do NOT produce audit records.
10. The audit logger does not emit records on health probe calls (`GET /health`).

## Known Gaps and Accepted Risks (Phase 1)

### Auth-denial events have no durable audit record

Auth denials (401/403) are intentionally excluded from audit records (they precede any scan
attempt). They are emitted as `WARNING` log lines in pod stdout only.

**Risk:** Repeated 401/403 events — indicative of credential probing or misconfigured callers
— leave no queryable record after pod restart. There is no alerting on auth-denial spikes
in Phase 1.

**Accepted for Phase 1 because:** Audit records live in pod stdout regardless (no durable
storage). Log aggregation and auth-denial alerting are Phase 2 concerns.

**Must be resolved in Phase 2** by: routing WARNING+ log lines to a durable aggregator
(Loki / CloudWatch) and defining an alert on sustained 401/403 rates per `correlation_id`
source IP.

### Audit record durability

Phase 1 audit records live in pod stdout. They are lost on pod restart with no replay path.

**Risk:** If a pod restarts during or immediately after a scan, the audit record for that
scan may be lost. There is no tamper-evidence or completeness guarantee.

**Accepted for Phase 1** as an explicitly understood limitation. Durable audit storage is
Phase 2 Stream 1.

---

## Out of Scope (this spec)

- Durable audit storage (database, S3, append-only file) — Phase 2.
  Phase 1 audit records live in pod stdout and are lost on pod restart.
  That is an accepted limitation for Phase 1.
- Audit record querying / dashboards — depends on log aggregation infrastructure.
- Per-tenant audit separation — Phase 2.
- Audit record signing or tamper-evidence — Phase 3+.
